# 设计决策

## 1. 用整数「分」计算，保证 TS 与 Python 逐位一致

**问题**：浮点让价（例如 `26 × 0.8`）在 JS 与 Python 的舍入行为不同（Python 的 `round` 是银行家舍入）。

**做法**：

- 引擎内部所有价格都是整数分，百分比一律用 `floor(a × pct / 100)`。
- 只对非负整数做除法，这样 JS 的 `Math.floor` 与 Python 的 `//` 结果相同。
- 只在输出时 `/100` 转回元。
- 价格文案由 `formatYuan(fen)` 用整数拼接生成，不依赖 `toFixed`。

## 2. 引擎一次算完，UI 按节拍展示

`runSession` 是纯函数，几毫秒内就能产出完整轨迹。UI 再按节拍逐条展示：每条气泡淡入 200ms，节拍间隔 450–900ms，并提供「跳过动画」。

这样带来三个好处：

- 单测、基准 fixture 和 Python 评测拿到的都是同一份完整轨迹。
- 演示节奏可以单独调，不影响逻辑。
- 刷新页面时（会话持久化在 sessionStorage）不会重放半截状态。

## 3. 底价不出现在买家侧

- 匹配卡只展示挂牌价、品相、信誉和评分。
- `MatchScore` 结构里本身就没有底价字段。
- 底价只在卖家回合内部用来计算报价。

## 4. 超预算的处理：拦截，而不是让买家默默放弃

当卖家报出底价、且只超出预算 ≤5%（`walkawayRule.nearMissPct`）时，买家 Agent「想」接受这个价格。G-BUDGET 会把这条 accept 消息标记为 `blocked`、不发送，并转给人工确认是否加价。

这让「预算硬上限」既在界面上看得见，又不可能被绕过。超出更多时，买家 Agent 则礼貌拒绝（`walkaway`）。

## 5. 消息解析失败用固定的卖家故障模拟

`mock/sellers.json` 里的 `glitch` 字段让指定卖家在指定轮次输出格式错误的消息：

| 卖家 | 故障方式 | 结果 |
|---|---|---|
| `seller_H` | 持续性：重试后仍然错误 | 转人工 |
| `seller_I` | 一次性：重试后恢复 | 继续议价 |

这样「重试一次 → 降级转人工」的两条路径都能确定性复现。

## 6. 评测的诚实性约束

- **不入库**：`latest_report.json`、`failures.jsonl`、`baseline.json`、`runs/` 都在 `.gitignore` 里，仓库不附带任何「跑过」的结果。
- **不判定达标**：目标值在脚本、UI、README 中一律标注 [待验证]，脚本只给数值。
- **不从输出反推预期**：样本的 `expected` 按设计意图人工标注，所以可能出现真实的不符合项。比如预算远低于所有挂牌价时，匹配打分中的价格分会全部归零，导致没有优先选择底价更低的卖家。这类问题应当由评测暴露出来，而不是被调整掉。
- **基线只建立、不预置**：首个成功运行只建立基线；比较键为「样本集版本 + 样本哈希 + 指标定义版本」。
- **取消或失败不留痕**：运行被取消或失败时，不写报告，不覆盖失败列表，任务也不能复跑。

## 7. 范围取舍

不做的内容：灰度、A/B、权限、真实 LLM、数据库、多卖家并行比价、信誉可视化，均记录在 README 的「后续要求」。

组件方面，技术栈中没有 shadcn/ui，因此只自写了少量 Tailwind 基础组件（Button / Card / Badge / Drawer），没有引入第二个组件库。
